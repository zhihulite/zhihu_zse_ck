# 方法论

## 0. 核心原则

1. **分层推进**：从最先加载的东西开始，一层只解决一件事，上一层结论是下一层的输入。不做「一次跳到底」的猜测。
2. **每层设证据门**：每层结束必须给出可复现证据（命令 + 真实输出 / 偏移 + 字节 / 逐字符比对）；证据不成立就停在本层。
3. **禁止暴力**：不在大参数空间里盲扫。搜索必须由已知明文或已知结构把未知量压到 ≤ 十几个候选。
4. **假设与结论分离**：每个结论标 `已验证` / `假设` / `未执行`；被否证的假设留在文档里（写明「曾假设 X，实测否证，证据 Y」）。
5. **单点吻合不算证据**：任何「A 对应 B」都要做整体吻合率对拍（1.7% vs 随机基线 2.2% ⇒ 否证）。

## 1. 分层模板

```
L0  JS 侧：谁加载它
      └ 找到加载点（WebAssembly.instantiate / eval / new Function），记录内嵌形态（base64？atob？）
L1  模块骨架：段表 / import / export / memory / 工具链 / name 段
      └ 门：import 与 export 清单完整；name 段条数与 code 段函数体数对得上（含 import 偏移）
L2  入口链：从 export 的 _start 走到真正的逻辑
      └ 门：说清静态 call 覆盖多少、哪些走 call_indirect
L3  库层：name 段里属于标准库的函数（runtime / syscall/js / encoding / strconv / reflect）
      └ 门：每个关心的能力都能指到具体函数名 + 文件偏移 + 大小
L4  自有代码层：作者自己的包
      └ 门：关键函数逐个反编译出语义，并说明调用关系
L5  数据层：内嵌的 blob / 程序 / 字符串池
      └ 门：结构与独立不变量对得上（如长度字段 == 词数）
L6  边界层：JS ↔ wasm 双向通道（import 调用 / copyBytesToGo / 宿主分派 marker）
      └ 门：每个方向的载荷形态说清（是值还是程序？加密了吗？跨 build 是否相同？）
```

层与层之间只允许「已被证据门确认的结论」传递。某层门没过，下一层结论必须标 `未验证`。

## 2. 每层该用的手段

| 手段 | 用途 |
|---|---|
| AST 提取（`@babel/parser`）而非正则 | 从混淆 JS 里取字符串表、访问器、轮转 IIFE |
| 已知明文反解 | 求加密密钥（不暴力）：用已知明文检测串 × 同长度密文 |
| 跨 build 逐字节比对 | 判「每 build 生成」还是「静态资产」 |
| 结构不变量交叉核对 | 验证解析正确（长度字段 == 元素数 × 宽度；池消费字节数 == 池大小） |
| 调用图分层（BFS） | 建立层次、发现共享核心 |
| name 段真名 + 偏移映射 | 给任意 code 偏移贴真名（`wasm_funcmap.json`） |
| 字节级断言 | 确认字段语义（如 `p0[20] += 1` ↔ 反编译第 6 行） |
| 多源互证 | 同一结论至少两条独立证据 |

## 3. 反模式

| 反模式 | 后果 |
|---|---|
| 在 wasm 文件里搜明文来否证「wasm 生成」 | 加密资产本来就不是明文，该否证不成立 |
| 单点吻合当证据 | 看似印证，整体对拍低于随机基线 ⇒ 否证 |
| 同函数共现当语义 | 把 `shr` + `or` 判成轮函数 ⇒ 假 ROTR；按 token 相邻 + 参数配对复检为 0 |
| 按自己预期解读文档 | 原文写「句柄表相关」读成「分派表」⇒ 据此推的结论作废 |
| 把假设写成结论 | 跨层套用密码方案，实测否证 |
| name 段索引直接配 code 段索引 | name 段含 import，需 `names[i+N_imports] ↔ bodies[i]` |
| 用 `find` 搜「已解码后的字节」 | 要找的是内嵌的**编码文本** |

## 4. 真机对拍差分法

适用场景：**字节码 / 程序 / 配置都逐字节相同，但行为不同**。此时静态分析无从下手（两边输入一样），
必须同时观测两个实现并找**第一条分歧**。

### 4.1 核心原则

不猜、不推推理链、不看总量。每个结论都必须由「真机与纯实现的同点对拍」给出，且每一步都能被证伪。
总量差异只用于判断「还没跑通」，定位必须靠第一条分歧。

### 4.2 操作规范

1. **先建真机基准**：用真 wasm + 站点自己的 glue + 手写环境跑一遍并插桩落盘。要对比任何量，先有这个基准。
2. **真机侧靠字节模式定位，不靠行号**：插桩工具按文件偏移插，偏移必须由指令字节模式反查，且模式必须**唯一命中**。
   > 陷阱：`i32.store offset=28` 的偏移常被折进基址计算，实际编码是 `36 02 00` —— 模式写错就 0 命中。
3. **纯实现侧探针必须抗位移**：一律按**文本锚点**插，绝不用行号。
   > 陷阱：按行号插的探针会被前面插入的标记顶偏，产生「物理上不可能」的假观测。
4. **只看第一条分歧**：总量差异只说明「还没跑通」。
5. **逐层下钻**，一次一层，每层问「谁写了它 / 谁决定了它」，直到落到最小单元（一个数值、一段字节）。
6. **每层先用 WAT 校验「这不是反编译 bug」**：下钻前先确认翻译忠实，否则会在错误前提上白挖。
7. **观测装置自相矛盾时，先怀疑装置**：出现「物理上不该有」的值时几乎总是探针问题。
   判据：真机同点若给出正常值，则另一侧的异常值必是探针错。
8. **先查坑单再动手**（`docs/PITFALLS.md`），避免重复劳动。
9. **任何「修复」都要有独立判据**；且始终分清「交付路径」与「支线」。

### 4.3 最小可复现步骤

1. **确认前提相同**：字节码逐词相同、VM 结构体基址相同、build 相同。前提不同先修前提。
2. **选一个可观测锚点**：两边都会经过、且能读到关键量的语句/指令。
3. **真机侧**：字节模式定位 → 插 `fd_write` 断点，把关键量落盘。
4. **纯实现侧**：文本锚点插同款探针，**输出字段顺序与真机对齐**（便于 `diff`）。
5. **对拍**：脚本找第一条分歧，打印分歧前后各 2–3 条。
6. **下钻**：把分歧点当新起点，重复 2–5。
7. **每层记录**：分歧点的实测值 + 排除了什么 + 下一步问什么。

### 4.4 已证伪的观察（避免重走）

| 曾经的判断 | 实测结论 |
|---|---|
| 「真机走 nil 分支、我走字符串分支」 | 错，两边都走字符串分支 |
| 「不是同一个 build」 | 错，同 build（`zh` 第 2 段逐字节相同） |
| 「`window` 只读是新坑」 | 错，早已记录并无条件修好 |
| 「操作数装载与解释执行是同一阶段」 | 错：pc 3–483 是**绑定解析**，pc≥560 才是**解释执行** |
| 「探针给出的布尔值出现在索引位是 VM 的问题」 | 错，探针被行号位移顶偏 |
